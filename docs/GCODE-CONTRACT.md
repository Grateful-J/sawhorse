# G-code development contract

Sawhorse currently exports geometry as DXF for CAM; it does not generate G-code. The offline contract in `src/nesting/gcode/` is a starting point for testing a future postprocessor, not a machine safety certification and not a general G-code validator. It is not connected to an export or to a controller.

## Evidence and scope

The local `.g-code` bundle identifies itself as Carbide Create. Inspection of printable strings in its executable identified separate GRBL, basic and Shapeoko postprocessor descriptions and explicit unit and absolute-mode commands. This does not identify which postprocessor or machine settings the operator uses, establish controller behavior, or prove a generated program safe. No code or fixture was taken from the bundle. Carbide 3D describes the Shapeoko 5 Pro 4x4 as having a nominal 48 × 48 inch cutting area, but this is not a usable work-coordinate travel envelope for a particular setup: [Carbide 3D](https://carbide3d.com/blog/introducing-shapeoko-5-pro/).

Carbide Create itself does have CAM and simulation capabilities: Carbide 3D describes simulation of toolpaths and the resulting stock, with rapid moves shown separately ([Carbide Create guide](https://my.carbide3d.com/pdf/carbide-create-v5.pdf)). Carbide Motion and the controller provide additional behavior; Carbide 3D documents, for example, alarms for hard and soft limits ([alarm codes](https://guides.carbide3d.com/faq/error-codes/)). The bundle's presence does not make those capabilities available to Sawhorse's tests, nor does inspecting strings establish which physical collision checks are implemented or enabled. A simulation can only account for the setup represented in it; actual workholding, tool length, offsets and machine state must match. These capabilities have not been independently validated here.

## Supplied pocket example

The supplied Carbide Create project `7-94-pocket shwoing as empty toolpath.c2d` contains three rectangular paths on `POCKET_7.94MM` whose narrow dimensions are approximately 5.7595 mm. Its pocket operation selects a 6.35 mm diameter #201 tool. The 7.94 mm layer suffix is the **cut depth**, not the pocket width. A 6.35 mm cutter cannot fit inside a 5.76 mm pocket, making this a concrete likely explanation for the empty toolpath; this has not been confirmed by rerunning Carbide Create. Fixing the tool choice or verifying the intended geometry is necessary; do not silently widen a joint to force a toolpath. The file is a CAM project, not an independent plain-text G-code example, so it does not establish the correct BitSetter or Carbide Motion output sequence. The user reports Carbide Motion build 667 and a BitSetter.

Future CAM checks must flag pockets too narrow for the selected tool and account for actual region geometry, tool diameter, stock-to-leave and tolerance, without treating a bounding-box test as proof that an arbitrary pocket is machinable. Empty toolpaths and omitted requested operations must fail validation rather than yield an apparently complete job.

The current synthetic contract only understands a small, explicit, millimetre, absolute, G54, linear-motion dialect. It rejects everything else, including arcs, tool changes, machine coordinates, offsets and modal-only motions. It requires explicit limits, spindle speeds, feeds, clearance and starting position, checks linear endpoints, forbids rapid motion below clearance, and requires the spindle off and Z at clearance at program end. Speeds, positions and limits in the tests are invented solely to exercise failures. Acceptance by this contract does not mean a program is valid for Carbide Motion or safe to run.

## Before enabling generation

- Identify the installed controller firmware and version, sender and version, spindle/router and speed control, and the actual postprocessor. Obtain representative user-generated programs for this exact setup and compare behavior with current Carbide 3D documentation and controller validation. Do not assume generic GRBL behavior matches every Carbide Motion workflow.
- Establish homing, tool measurement and tool-change behavior, active offsets and work-zero conventions, actual machine travel and the transformation between work and machine coordinates. Require a verified initial position; unknown positions and offsets must block export. Bounds of a work-coordinate box alone do not establish machine travel.
- Define actual stock, spoilboard, clamps and fixtures, tool dimensions and stickout, safe heights, spindle settings, and material- and tool-specific feeds, stepdowns and operation depths. Check the full swept tool and holder path, including initial entry, cutting, retracts and repositioning. Clearance is not universal and can exceed available Z travel.
- Test geometry and cut order, compensation, pocket coverage, tabs, depths, tool identity, passes, units, formatting/rounding, invalid numeric inputs and all modal state transitions. Validate output with an independent interpreter against the target controller and compare representative jobs with reviewed CAM output. Test fail-closed behavior for every unsupported operation.
- Review toolpaths in the intended sender and simulator; follow the machine manufacturer's commissioning and dry-run procedures under supervision before any cutting. Parser acceptance alone cannot prove that workholding, cutter, stock or motion are safe.

The current contract does not check fixture collisions, material removal, tool geometry, offsets, physical travel, controller state, acceleration, tool changes, a sender's special commands, or whether any commanded motion achieves the intended part. It must not be presented as a safety gate for real machining. Generic GRBL documents a parser check mode, but its availability and meaning for this particular firmware and sender must be verified: [GRBL interface documentation](https://github.com/gnea/grbl/blob/master/doc/markdown/interface.md).
