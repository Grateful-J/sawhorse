# Shapeoko 5 Pro 4x4: test research

## Status: no machine-ready G-code

At worktree base `28e1158`, Sawhorse writes DXF and does not contain a G-code postprocessor. There is therefore no Sawhorse G-code generator in this worktree to test, and no passing test here verifies a program against Carbide Motion or a machine. The tests in `src/nesting/gcode` provide DXF regression coverage and an experimental, intentionally restricted linear-program checker for synthetic test inputs. The checker rejects tool changes, arcs, machine-coordinate moves, offsets and other commands. It is not connected to DXF export, a postprocessor, Carbide Motion or a controller, and must not be used to approve machining.

This research concerns the reported Shapeoko 5 Pro 4x4, BitSetter, and Carbide Motion build 667 (reported release date 2026-08-01). The 48 × 48 inch cutting area published by Carbide 3D is nominal, not a verified work-coordinate envelope for the installed machine and fixtures. [Shapeoko 5 Pro](https://carbide3d.com/blog/introducing-shapeoko-5-pro/)

## Evidence and compatibility traps

- The local bundle is Carbide Create; another bundle is Carbide Motion. Binary strings reveal a Shapeoko-specific post description and BitSetter-related implementation, but do not establish what build 667 does for every file. The supplied `.c2d` is a project, not an independently readable Shapeoko G-code sample. Its three `POCKET_7.94MM` paths are about 5.7595 mm wide, while the operation selects a 6.35 mm cutter. The layer suffix is depth. This dimensional mismatch likely explains the empty toolpath; it was not confirmed by rerunning Carbide Create.
- The installed Create executable contains text for a Shapeoko postprocessor that describes machine-coordinate Z retraction, metric or inch units, compressed modal motion, `M6` with a tool number, spindle commands and `M02` at the end. This is evidence about a postprocessor bundled in this local application, not proof of the behavior of the user's specific saved project or Motion build. In particular, the restricted test checker rejects several of these forms and cannot be used to validate real Shapeoko post output. No postprocessor code was incorporated into this repository.
- [Carbide 3D's supported G-code list](https://guides.carbide3d.com/faq/supported-gcodes/) distinguishes the sender's `M6` handling from generic controller behavior, says `G54`–`G59` are accepted but ignored, and notes special program-end behavior. The experimental checker's required `G54` is only a synthetic format convention; it does **not** prove a work offset has been selected or validated in Carbide Motion.
- Carbide 3D's [BitSetter workflow update](https://carbide3d.com/blog/bitsetter-changes-carbide-motion/) describes measuring after Z zero is set. Its [Shapeoko Pro guide](https://carbide3d.com/files/pdf/Shapeoko_Pro_assembly_guide_02-05-2021_v1_web.pdf) calls for the Carbide 3D Shapeoko postprocessor with BitSetter. Exact build-667 sender behavior and post output need direct testing; do not infer it from generic GRBL.
- Carbide 3D documents [simulation](https://guides.carbide3d.com/create/simulation/) and [limit alarms](https://guides.carbide3d.com/faq/error-codes/); neither establishes the actual workholding, offsets, tool, stock or machine state. A parser check cannot prove physical clearance or cut quality.

## Required generator acceptance work

1. Connect tests directly to the actual generator entry point, using representative jobs and rejection cases. Make a missing generator, missing requested operation, empty output, and unsupported operation fail the release gate; never skip silently. Validate both the generated text and the requested-to-generated operation mapping.
2. Obtain reviewed, independently generated Shapeoko postprocessor examples for build 667, including single- and multi-tool jobs. Check sender acceptance and expected prompts in a controlled, disconnected or vendor-supported environment. Confirm `M6`, tool identifiers, spindle stop/restart, Z measurement, offsets, `M2`/`M30`, comments, and units against this version. No actual reference G-code has been supplied yet.
3. Independently interpret the complete emitted dialect with explicit modal state, both units, coordinate frames, offsets, line and arc sweeps, feed/spindle state, tool changes, and sender-generated moves. Refuse unsupported or ambiguous constructs. Compare output to operation geometry, depths, ordering, tabs and cutter sweeps; test pocket coverage and unacceptable remaining material, not only endpoints.
4. Require explicit verified machine-coordinate limits, homing and work-offset state, stock, clamps, spoilboard, tool and holder geometry, tool length, safe travel and feed/spindle constraints. Check the full swept volume including first movement, rapids, tool changes, sender-inserted moves and program end. A test profile's invented dimensions must never become machine defaults.
5. Exercise boundary values, numeric rounding, malformed input, omitted or duplicate operations, narrow pockets, 5 mm holes with a 6.35 mm tool, wrong Z-zero convention, invalid stock and multi-tool changes. Independently validate and simulate; follow Carbide 3D procedures for commissioning and supervised dry runs before cutting. No automated test alone guarantees physical safety.

## Run the current tests

From this worktree, after installing the repository dependencies: `npm test -- src/nesting/gcode`. The narrow-pocket DXF tests inspect actual export with an independent parser in both supported DXF forms. The synthetic linear-checker tests exercise its own rejection logic only; passing them does not show that Carbide Motion accepts any output or that a toolpath is safe.

`python3 scripts/check-c2d-pocket-width.py PATH.c2d` inspects a **closed** Carbide Create project read-only. For layer-selected pocket paths, it reports when a shape's axis-aligned bounds, including curve control points, are narrower than the selected cutter. The diagnostic found three such shapes in the supplied example. It exits 1 on findings and 2 on unsupported selection or malformed input. A zero exit code only means that this particular necessary-condition check found nothing; it does not show that geometry, cutting, fixtures or toolpaths are safe. This is not a Carbide Create interpreter: it cannot fully analyze islands, overlapping regions, cutter sweeps, tolerance, stock-to-leave, generated toolpaths, or the sender. Its own synthetic tests run with `python3 scripts/test-check-c2d-pocket-width.py`.

The supplied drawer-front DXF has three profiles and six 4.7625 mm through-hole circles on `DRILL_D4.76MM_THRU`. Its corresponding Create project selects those hole vectors in a drilling operation using a 6.35 mm #201 and an end depth of 13 mm, with 19.05 mm project stock. The user explained the #201 was selected for every operation in this example. A drilling operation locates holes from closed vectors ([Carbide 3D](https://carbide3d.com/blog/carbide-create-527/)); the tool determines the drilled diameter ([Carbide 3D support](https://community.carbide3d.com/t/i-think-i-used-the-drill-toolpath-incorrectly/75843)). These settings therefore differ from the DXF's diameter and through-hole intent. This is a comparison of saved settings, not evidence that any cut was run or that actual stock matches the project. The profile operation also records `ignore_tabs: true`; confirm the intended workholding in CAM.

`python3 scripts/check-c2d-drilling.py PATH.c2d` reports discrepancies between saved layer-selected drilling settings and Sawhorse-style `DRILL_D...` layer names, including through-depth against the project stock thickness. It exits 1 for findings, 2 for unsupported or invalid inputs, and its zero result only means that the limited comparisons found no discrepancy. It does not inspect actual toolpaths or prove that a tool, stock, workholding or cut is safe. Run its synthetic tests with `python3 scripts/test-check-c2d-drilling.py`.

## Tool inventory and layer names: integrated

The shop library now records explicit ownership and confirmed collet sizes. Seed entries are unconfirmed. CNC/DXF preflight reads the job sheet's per-layer assignments and measured widths, including its narrow-groove fallback, and warns about missing tools, unconfirmed ownership, unknown/incompatible shanks and collets, insufficient cutting length, and width failures. It checks through cuts against sheet thickness plus 0.5 mm. Approximate outline measurements are explicitly flagged. These checks are necessary conditions, not a swept-toolpath or machine-state simulation.

CNC layer names append the assigned tool name and diameter and say `POCKET_WITH` for holes, making clear that a circle is pocketed with a smaller end mill. Unknown tools and unconfirmed ownership are marked. The job sheet and cut order use the same names. Export captures shop settings before measurement and renders all DXFs and job sheets before opening save dialogs. Combined DXF/R12 exports retain the original names; CNC setup's Job sheet tab can disable tool-labelled names for existing layer templates. The layer parser accepts both forms.

No specific Carbide catalog number is inferred from a generic starter tool. Give a confirmed cutter its actual catalog/library name and measured dimensions in CNC setup to carry that identity into the layer. In particular, a generic #102 must not be assumed to reach through 19.05 mm stock or fit the collet without checking its actual dimensions.

Run `NODE_ENV=test npm test -- src/nesting/gcode` and `python3 scripts/test-check-c2d-pocket-width.py` and `python3 scripts/test-check-c2d-drilling.py`. A clean result does not establish generated G-code compatibility: Sawhorse continues to export DXF for external CAM, not G-code.
